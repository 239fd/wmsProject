## 1. Резюме по содержимому `ИНФО/`

### 1.1 `Готовое_решение_..._продажу_на_экспорт_товаров.pdf` (актуально на 25.02.2026, ООО «ЮрСпектр»)

**Ключевые тезисы для нашей реализации:**

1. **Основной первичный документ при экспорте — ТН** (товарная накладная) на бумажном носителе. Независимо от вида транспорта. К ТН прилагается **транспортный документ**:
   - **CMR-накладная** — при доставке автотранспортом.
   - ж/д накладная (грузобагажная квитанция) — ж/д.
   - Квитанция о приёме почтового отправления — почта.
   - Авиационная накладная — воздушный.
2. В ТН в строке **«Товар к доставке принял»** указываются наименование и реквизиты прилагаемого транспортного документа. Только связка ТН + транспортный документ является основанием для **списания товара с учёта**.
3. **При экспорте за валюту** — стоимостные показатели в ТН отражают **в валюте договора купли-продажи**. В шапке таблицы товарного раздела слова «руб. коп.» зачёркиваются, вместо них пишется сокращённое наименование валюты (USD, EUR, RUB, ...). Аналогично — в строках «Всего сумма НДС» и «Всего стоимость с НДС».
4. **Если цена в одной валюте, расчёт в другой** — ТН выписывается **в валюте цены договора**, не валюте расчёта.
5. **ЭСЧФ** (электронный счёт-фактура НДС) — направляется только на Портал МНС, покупателю не выставляется. **Не наш scope** (МНС-инфраструктура). Хорошо, что `invoice-fact` дропнут.
6. **ЭТТН/ЭТН** (электронные накладные) **обязательны** для:
   - Товаров из перечня N 1030 (постановление о маркировке) при операциях с маркированными товарами.
   - Прослеживаемых товаров (перечни 1/2 постановления N 250 / Указ N 496).
   - Для торговли в пределах ЕАЭС — ЭТТН/ЭТН **дополнительно** к бумажной ТН (электронные не считаются ПУД).
7. С **01.01.2026** действуют новые правила оформления CMR-накладной и заказа-поручения (см. постановление N 9/75/35/26).
8. Обязательные реквизиты для электронных накладных: **GLN** (международный ID грузоотправителя), **код и наименование страны грузоотправителя/грузополучателя**.

### 1.2 `Постоновление о примке товаров.pdf` (Постановление Совмина РБ N 1290 от 03.09.2008, ред. от 13.10.2017)

**Положение о приёмке товаров по количеству и качеству** — детальный порядок, обязательный для всех договоров купли-продажи между юр. лицами и ИП в РБ.

#### Сроки приёмки (ГЛАВА 3, ключевое для нашего workflow)

| Тип товара / приёмки | Срок |
|---|---|
| Товар без тары, в открытой/повреждённой таре | В момент получения, не позже сроков разгрузки |
| Закрытая тара, по массе нетто и кол-ву ед. | **не позже 10 дней** |
| Скоропортящийся товар (количество) | **не позже 24 часов** |
| Приёмка по качеству — из другого пункта | **не позже 20 дней** |
| Приёмка по качеству — из этого пункта | **не позже 10 дней** |
| Скрытые недостатки | акт **в течение 24 часов** с обнаружения |

#### Workflow при выявлении недостачи/несоответствия (ГЛАВА 4 п.25, ГЛАВА 5 п.29)

1. **Приостановить** приёмку.
2. Принять меры по обеспечению сохранности товара, предотвращению смешения.
3. **Вызвать представителя продавца** (уведомление не позже 24 часов, скоропортящийся — безотлагательно). Уведомление — телеграф/факс/срочная связь.
4. Представитель из того же населённого пункта — явка не позже следующего дня (скоропортящийся — 4 часа); из другого — 3 дня + время проезда.
5. При неявке — приёмка с иным представителем (ТПП / гос. орган / аккредитованная лаборатория).
6. **Оформить акт** в день выявления недостачи/несоответствия.
7. Акт **утверждается руководителем** не позже следующего дня после составления.

#### Обязательные реквизиты акта приёмки (ГЛАВА 6 п.40 — это и есть `discrepancy-act`)

25+ полей, в том числе:
- Наименование и адрес организации, проводившей приёмку.
- Адрес проведения приёмки.
- Номер и дата акта; **время начала и окончания** приёмки.
- ФИО, должность, место работы лиц-участников.
- Наименование и адрес продавца.
- **Дата и номер уведомления о вызове представителя продавца**.
- **Номер и дата договора**.
- Номер и дата счёт-фактуры и **транспортной накладной** (ТТН).
- Номер и дата документа, удостоверяющего качество товара.
- Даты отправки/прибытия товара, время выдачи перевозчиком, вскрытия пломб.
- Условия хранения, средства измерений (с поверкой!).
- **Состояние и недостатки тары/упаковки**, дата вскрытия.
- Состояние пломб, кто пломбировал/взвешивал.
- Общая масса (фактическая + по документам), масса каждого грузового места.
- Транспортная и отправительская маркировка.
- Способ определения количества недостающего товара.
- Количество/масса/полное наименование товара + **забракованный товар**.
- Некомплектный товар, недостающие части, их стоимость.
- ТНПА/эталоны для проверки качества.
- Номер работника службы контроля качества изготовителя (если на товаре указан).
- Сведения об отборе образцов.
- Стоимость недостающего товара.
- **Заключение о причинах** недостачи.
- **Излишки** (если выявлены) — не только недостача!

**К акту прилагаются** (п.44): копии сопроводительных документов, упаковочные ярлыки, квитанции взвешивания, **пломбы с грузовых мест с недостачей**, заверенная копия транспортного документа, документ о полномочиях, ведомости подачи вагонов, акт отбора образцов + заключение анализа, прочие (анализ влажности, температурный режим).

## 2. Несоответствия ИНФО vs текущая реализация WMS

Я подробно прошёлся по DocumentService / DocumentRpaService / DTO. Ниже — где код **не соответствует** или **отсутствует** относительно требований бел. законодательства из ИНФО.

### 2.1 receipt-act vs discrepancy-act — концептуальное наложение

**По Постановлению N 1290 ГЛАВА 6 п.39:** *«Если при приёмке товаров по количеству и качеству будут выявлены недостача товара или его ненадлежащее качество, то результаты приёмки оформляются актом».*

То есть **акт приёмки составляется ТОЛЬКО при недостаче/несоответствии** — это и есть `discrepancy-act`. **Отдельного «акта приёмки при нормальной приёмке» в бел. праве нет** — для нормальной приёмки достаточно подписанной ТТН/ТН.

**Что у нас:** разделены `receipt-act` и `discrepancy-act` как два независимых endpoint'а. Это некорректно.

**Варианты:**
- Объединить в один `discrepancy-act` (как по закону).
- Оставить `receipt-act` как внутренний документ организации (для DIRECTOR — формальная приёмка по договору с поставщиком), не первичка. Но тогда не соответствует п.39.
- Поскольку у пользователя есть шаблон `Акт приемки.RTF` — возможно, имелся в виду именно акт при расхождении. Нужно уточнить.

**Вопрос пользователю: Q1** (см. §3).

### 2.2 DTO для discrepancy-act не покрывает обязательные реквизиты п.40

Сейчас в `document-service/dto/` нет `DiscrepancyActData`. Из 25+ полей п.40, которые **должны быть в акте**, в нашей модели данных в принципе отсутствуют:

- Время начала и окончания приёмки.
- Адрес проведения приёмки (склад покупателя или иной).
- Дата и номер уведомления о вызове представителя продавца.
- Номер и дата договора с поставщиком (Supply / Supplier — не хранится отдельно).
- Номер и дата документа, удостоверяющего качество товара (сертификат / паспорт).
- Состояние пломб, кто пломбировал/взвешивал.
- Транспортная маркировка.
- Способ определения количества недостающего товара.
- ТНПА/эталоны для проверки качества.
- Заключение о причинах недостачи (свободный текст).
- **Излишки** (excess) — не только недостача.
- Утверждение руководителем (двойная подпись).
- Приложения (минимум 7-8 типов: копии документов, ярлыки, пломбы, акт отбора образцов).

**Что у нас:** DTO `ReceiptOrderData` имеет общие шапочные поля + items. Для discrepancy-act нужен **сильно расширенный** DTO с полями выше.

### 2.3 Workflow приёмки не учитывает обязательные шаги ГЛАВА 4 п.25 / ГЛАВА 5 п.29

В `OperationController.receiveProduct` сейчас:
```
POST /receive → receiveProduct() → save operation → generateReceiptOrder → return 201
```

**Не реализованы шаги при выявлении недостачи** (которые требует Положение):
1. **Приостановка приёмки** — нет статуса `PAUSED` у ProductOperation. Нет endpoint'а «приостановить».
2. **Уведомление поставщику** — нет интеграции SMTP / RabbitMQ для отправки. organization-service умеет SMTP (`mail.gmail.com`), но для этого нужен endpoint `/api/operations/{id}/notify-supplier`.
3. **24-часовой таймер** для отправки уведомления — нет.
4. **Регистрация ответа представителя** — нет (явится / не явится, ETA).
5. **Привязка `discrepancy-act` к `operationId`** — сейчас документы хранятся в in-memory `ConcurrentHashMap` без связи с операциями.

### 2.4 Сроки приёмки не валидируются

По Постановлению — жёсткие сроки (10 дней / 20 дней / 24 часа). У нас:
- В Product / Batch entity **нет поля `perishable: boolean`** или `shelfLifeHours`. Скоропортящийся товар не отличается на уровне модели.
- В Receive operation **нет timestamps**: `receivedAt`, `qualityCheckDeadline`. Нет валидации «не позже 10 дней».
- UI не показывает таймер до истечения срока приёмки по качеству.

### 2.5 Экспортный флоу — не реализован отдельно

По первому PDF — при экспорте нужны:
1. **ТН** в валюте договора.
2. **CMR** (или ж/д накладная / квитанция / авиа).
3. В ТН — строка «Товар к доставке принял» с указанием реквизитов CMR.
4. **Валюта НДС** в строках «Всего сумма НДС» и «Всего стоимость с НДС».

**Что у нас:**
- В `ShipmentRequest` нет поля `shipmentType: DOMESTIC | EXPORT`.
- В DTO документов нет поля `currency: String` (3 буквы валюты).
- ТН и CMR — два разных endpoint'а; **нет связки «один экспорт → пакет из 2 документов»**.
- В saga `DOCUMENT_GENERATION` step хранит один `documentId` — не несколько.
- Нет полей `GLN`, `countryFrom`, `countryTo` в DTO (это нужно для ЭТТН/ЭТН, но мы их и не делаем — см. §2.6).

### 2.6 ЭТТН/ЭТН — за пределами scope

Электронные накладные требуют интеграции с системой электронного обмена данными РБ (РУП «НЦЭУ», МНС). Это **не наш scope** для диплома.

**Но**: для маркированных товаров (перечень N 1030) и прослеживаемых (N 250 / Указ N 496) система **юридически непригодна** без ЭТТН/ЭТН. Это нужно явно зафиксировать как **ограничение** в пояснительной записке к диплому — «WMS не поддерживает товары, подлежащие обязательному маркированию средствами идентификации и прослеживаемости; для них требуется ЭТТН/ЭТН-инфраструктура, не входящая в scope дипломного проекта».

### 2.7 Инвентаризация — нет привязки к НСБУ N 126

`InventoryCheck` есть, генерирует `inventory-report` (опись). **Не реализовано**:
- В DB **нет признака причины** инвентаризации (плановая / реорганизация / смена МОЛ / факт хищения / по решению руководителя).
- Нет связи **инвентаризации с годовой отчётностью** и нет напоминания «до 30 сентября / 30 ноября».
- В UI нет справочного блока про обязательные случаи и сроки.
- Председатель комиссии + члены — поля в DTO есть, но в UI не валидируется минимум 3 человека (по практике).

### 2.8 Подписи и роли — Положение требует «ФИО, должность, место работы»

User entity имеет `firstName`, `lastName`. **Нет**:
- `middleName` (отчество).
- `position` (должность).
- `workplace` (структурное подразделение, если разное от organizationName).

В discrepancy-act это **обязательные** реквизиты для каждого участника.

### 2.9 Хранение документов — in-memory, теряется при рестарте

`DocumentService.records` = `ConcurrentHashMap<UUID, DocumentRecord>`. Рестарт → потеря всех документов и метаданных.

**Постановление N 1290 п.45:** *«Акты приёмки товаров по количеству и качеству регистрируются и хранятся в порядке, установленном покупателем».*

То есть **юридически документы должны храниться**. Два варианта:
- Сделать document-service stateful: добавить таблицу `generated_documents` в одну из существующих БД (логичнее — в product_db, поскольку документы привязаны к операциям).
- Оставить document-service stateless, регистрацию вести в `product-service.GeneratedDocument` entity (ссылка на operationId + documentType + documentNumber + generatedAt). Файл регенерируется по требованию (`GET /api/documents/{id}` это уже делает).

Второй вариант проще и не нарушает архитектуру.

### 2.10 Документ-нумерация — нет генератора

В DTO есть `documentNumber: String`, но **никто его не выставляет** автоматически. Сейчас, видимо, прокидывается из payload (или random). По бел. практике — каждый тип документа имеет свою серию (например, «ПО-2026-00001» для приходного ордера). Нужен `DocumentNumberService` per organization + type + year.

## 3. Вопросы, которые надо обсудить (перед HP-1)

### Q1. receipt-act = discrepancy-act?

По N 1290 п.39 акт составляется **только** при выявлении недостачи/несоответствия. Загруженный `Акт приемки.RTF` — это, скорее всего, **именно акт при расхождении**, не акт нормальной приёмки.

**Варианты:**
- (a) Объединить — оставить только `discrepancy-act`, эндпоинт `receipt-act` дропнуть.
- (b) Оставить `receipt-act` как внутренний документ организации (не первичка). Тогда `Акт приемки.RTF` подключить к `discrepancy-act`, а для `receipt-act` сгенерить упрощённый PDF.
- (c) Использовать `Акт приемки.RTF` для обоих (один шаблон, разное наполнение).

**Что выбрать?**
